# 手势识别投票机制 + 冷却机制说明

## 问题背景

在使用滑动窗口进行手势识别时，容易在以下时刻产生误识别：
- **手势开始时**：窗口前半部分是旧数据（idle 或其他手势）
- **手势结束时**：窗口后半部分是新动作数据
- **手势完成后**：手臂回到静止位置时产生额外的加速度变化

例如：做一个"向左"手势时，可能在窗口边界识别出 "right" 或 "push"，手势完成后又可能误识别为其他手势。

## 解决方案：多数投票 + 置信度过滤 + 冷却机制

### 核心思想

1. **投票机制**：只有当一个手势在连续多次推理中稳定出现且置信度足够高时，才确认为有效手势
2. **冷却机制**：确认手势后进入冷却期，在此期间忽略所有推理结果，避免连续误触发

### 实现机制

```
原始推理流 → 冷却检查 → 置信度过滤 → 投票缓冲区 → 多数投票 → 确认手势 → 启动冷却
                ↓                                                              ↓
            忽略推理                                                    清空投票缓冲区
```

### 配置参数

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `VOTE_WINDOW_SIZE` | 5 | 投票窗口大小（最近 N 次推理） |
| `VOTE_THRESHOLD` | 3 | 投票阈值（至少 M 次相同） |
| `MIN_CONFIDENCE` | 0.65 | 最低置信度（低于此值不参与投票） |
| `COOLDOWN_MS` | 1200 | 冷却时间（毫秒），确认手势后的静默期 |

### 工作流程

1. **冷却检查**：
   - 如果在冷却期内，直接忽略本次推理
   - 如果冷却期结束，继续处理

2. **每次推理后**：
   - 检查置信度是否 ≥ 0.65
   - 如果是，将结果加入投票缓冲区
   - 如果否，忽略此次推理

3. **统计投票**：
   - 统计最近 5 次推理中每个类别的出现次数
   - 找到票数最多的类别

4. **确认手势**：
   - 如果某个类别的票数 ≥ 3，确认为该手势
   - **如果是 idle**：更新全局状态，但不启动冷却
   - **如果是其他手势**：
     - 更新全局状态，触发 BLE 通知
     - 启动冷却期（1.2 秒）
     - 清空投票缓冲区（避免旧数据影响下次识别）
   - 如果没有类别达到阈值，不更新状态

5. **冷却期内**（仅针对非 idle 手势）：
   - 所有推理结果被忽略
   - 不显示调试信息（减少串口输出）
   - 等待冷却时间结束

### 示例场景

#### 场景 1：稳定的"向左"手势 + 冷却 ✅

```
推理序列：
1. left  (0.72) → 加入投票
2. left  (0.68) → 加入投票
3. left  (0.75) → 加入投票 → ✓ 确认 "left" (3/5)
   → 启动冷却 (1200ms)
   → 清空投票缓冲区
4. [冷却期] 忽略所有推理
5. [冷却期] 忽略所有推理
6. [冷却期] 忽略所有推理
... (约 1.2 秒后)
7. [冷却结束] 可以识别下一个手势
```

#### 场景 2：idle 状态不触发冷却 ✅

```
推理序列：
1. left  (0.72) → 加入投票
2. left  (0.70) → 加入投票
3. left  (0.68) → 加入投票 → ✓ 确认 "left" (3/5)
   → 启动冷却
4. [冷却期] 忽略推理
... (1.2秒后)
5. idle  (0.85) → 加入投票
6. idle  (0.88) → 加入投票
7. idle  (0.90) → 加入投票 → ✓ 确认 "idle" (3/5)
   → 更新状态为 idle
   → 不启动冷却（idle 不需要冷却）
8. left  (0.70) → 可以立即开始识别下一个手势
```

#### 场景 3：边界误识别被过滤 ✅

```
推理序列：
1. idle  (0.85) → 加入投票
2. right (0.58) → 置信度低，忽略
3. left  (0.70) → 加入投票
4. left  (0.72) → 加入投票
5. left  (0.68) → 加入投票 → ✓ 确认 "left" (3/5)
   → 启动冷却
```

#### 场景 4：手势完成后的误触发被冷却阻止 ✅

```
时间轴：
T=0.0s: 用户做"向左"手势
T=0.3s: 投票确认 "left" → 启动冷却
T=0.4s: 手臂回到静止位置（产生加速度变化）
        → 推理可能识别为 "right" 或其他
        → 但在冷却期内，被忽略 ✓
T=1.5s: 冷却结束，可以识别下一个手势
```

#### 场景 5：不稳定的手势被拒绝 ❌

```
推理序列：
1. left  (0.70) → 加入投票
2. right (0.68) → 加入投票
3. left  (0.65) → 加入投票
4. up    (0.72) → 加入投票
5. left  (0.69) → 加入投票 → ✗ 没有类别达到 3 票
```

## 参数调优指南

### 保守配置（适合演示/答辩）

```cpp
#define VOTE_WINDOW_SIZE 7
#define VOTE_THRESHOLD 5
#define MIN_CONFIDENCE 0.70f
#define COOLDOWN_MS 1800  // 1.8秒
```

- 优点：误触发率极低，识别准确
- 缺点：响应稍慢，需要更长的手势持续时间

### 激进配置（适合熟练用户）

```cpp
#define VOTE_WINDOW_SIZE 3
#define VOTE_THRESHOLD 2
#define MIN_CONFIDENCE 0.60f
#define COOLDOWN_MS 800   // 0.8秒
```

- 优点：响应快速，手势可以更短
- 缺点：可能有少量误触发

### 平衡配置（推荐）⭐

```cpp
#define VOTE_WINDOW_SIZE 5
#define VOTE_THRESHOLD 3
#define MIN_CONFIDENCE 0.65f
#define COOLDOWN_MS 1200  // 1.2秒
```

- 在准确性和响应速度之间取得平衡
- 适合大多数使用场景

### 冷却时间调优建议

| 使用场景 | 推荐冷却时间 | 说明 |
|---------|-------------|------|
| PPT 演示 | 1500-2000ms | 演讲时手势间隔较长 |
| 游戏控制 | 800-1000ms | 需要快速连续操作 |
| 日常使用 | 1200-1500ms | 平衡准确性和响应速度 |
| 调试测试 | 500-800ms | 快速测试多个手势 |

## 调试输出

启用投票+冷却机制后，串口输出示例：

```
[Inference] IMU initialized successfully
[Inference] Voting: window=5, threshold=3, min_conf=0.65
[Inference] Cooldown: 1200 ms

[Inference] Raw: idle (0.85)
[Inference] Raw: left (0.72)
[Inference] Raw: left (0.68)
[Inference] Raw: left (0.75)
[Vote] ✓ Confirmed: left (votes: 3/5)
[Cooldown] Started (1200 ms)
[Inference] >>> CONFIRMED: left (seq=42) <<<

... (冷却期内无输出) ...

[Cooldown] Ended (duration: 1203 ms)
[Inference] Raw: idle (0.88)
```

### 输出说明

- `[Inference] Raw:` - 每次原始推理结果（冷却期内不显示）
- `[Vote] ✓ Confirmed:` - 投票确认的手势
- `[Cooldown] Started` - 冷却期开始
- `[Cooldown] Ended` - 冷却期结束
- `[Inference] >>> CONFIRMED:` - 最终确认并更新全局状态

## 性能影响

- **内存开销**：28 字节（5 个 int + 2 个 uint32_t + 1 个 bool）
- **计算开销**：可忽略（简单的数组遍历和时间比较）
- **延迟增加**：
  - 投票延迟：约 100-200ms（取决于窗口大小）
  - 冷却延迟：1200ms（手势间最小间隔）
  - 总响应时间：约 1.3-1.4 秒/手势

## 双层冷却策略

系统采用**嵌入式端 + PC 端**双层冷却：

| 层级 | 冷却时间 | 作用 |
|------|---------|------|
| 嵌入式端 | 1.2 秒 | 防止连续误触发，减少无效 BLE 传输 |
| PC 端 | 2.0 秒 | 防止用户连续操作，提供额外保护 |

这种设计既节省了 BLE 带宽和功耗，又提供了双重保险。
